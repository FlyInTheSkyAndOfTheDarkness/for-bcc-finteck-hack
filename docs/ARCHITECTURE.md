# Архитектура reqcheck

Документ описывает устройство агента: контракты данных, стадии конвейера, маршрутизацию моделей, инфраструктуру LLM и точки расширения. Быстрый старт и команды запуска см. в [README](../README.md).

## 1. Общая схема

```
файл ─► [1 Ingest] ─► [2 Segment] ─► [3 Linters] ──┐
                          │                         ▼
                          └──────────► [4 Req-Review] ─► [5 Set-Review] ─► [6 Critic] ─► [7 Clarify] ─► [8 Report]
                                                                                              ▲   │
                                                                          ответы автора ──────┘   └─ итог (Verdict)
инфраструктура: LLMClient (кэш · rate limit · retry · fallback) · pydantic-схемы · trace.jsonl · версия промптов
```

Оркестратор `reqcheck/pipeline.py: run()` вызывает стадии по очереди и возвращает `ReportData`. Стадии не знают друг о друге: они обмениваются только объектами из `models.py`. К LLM стадия обращается через единственный метод `LLMClient.generate_json(system, user, schema, *, tag)`.

Принципы:

1. **Любое замечание привязано к цитате.** `Finding.quote` проверяется по тексту документа (`grounding.py`), результат хранится в `Finding.grounded`.
2. **Детерминированное ядро.** Нарезка и линтеры работают без LLM, поэтому режим `--provider fake` и тесты не зависят от сети.
3. **Сбой LLM не роняет прогон.** Параллельные задачи изолированы (`engine/parallel.py`): упавший пакет даёт пустой результат, остальные продолжают работу; ответ, не прошедший схему, перезапрашивается один раз.
4. **Структурированный вывод.** Каждый вызов LLM возвращает pydantic-объект по схеме из `schemas.py`.

## 2. Контракты данных

### `reqcheck/models.py` — доменные объекты

| Класс | Ключевые поля |
| :--- | :--- |
| `Block` | `id`, `part`, `section_path[]`, `kind` (text, table_row, list_item, code, heading), `text`, `line_start/end`, `page`; метод `locator()` даёт человекочитаемое место |
| `Document` | `name`, `format`, `sha256`, `blocks[]` |
| `Requirement` | `rid` («R-01»), `doc_id` («Ф-1» или `None`), `kind` (`ReqKind`), `summary`, `quote`, `block_ids[]`, `location`, `grounded` |
| `Finding` | `fid` («D-001»), `scope` (requirement / set), `rids[]`, `criterion` (`Criterion`), `severity`, `title`, `quote`, `location`, `explanation`, `recommendation`, `source`, `confidence` 0..1, `verified`, `grounded` |
| `Question` | `qid`, `fids[]`, `rids[]`, `question`, `why`, `options[]`, `answer` |
| `RunPassport` | `doc_name`, `doc_path`, `doc_sha256`, `doc_format`, `run_at`, `provider`, `model`, `agent_version`, `prompt_version`, `params`, `llm_calls`, `tokens_total`, `duration_s` |
| `SetSummary` | `criteria{критерий → статус и комментарий}`, `notes[]` |
| `Verdict` | `ready_for_development`, `ready_for_testing`, `rationale`, `top_fixes[]` |
| `ReportData` | `passport`, `requirements[]`, `findings[]`, `questions[]`, `set_summary`, `verdict` |

Перечисления:

- `Severity`: `critical` (блокирует разработку или тестирование: противоречие, непроверяемость, ключевой пропуск), `major`, `minor`.
- `FindingSource`: `linter`, `llm_requirement`, `llm_set`, `scenario` (критерий приёмки против правил), `fintech`.
- `Criterion`: 9 критериев отдельного требования ISO 29148 §5.2.5 (`necessary`, `appropriate`, `unambiguous`, `complete`, `singular`, `feasible`, `verifiable`, `correct`, `conforming`); 6 критериев набора §5.2.6 (`set_complete`, `set_consistent`, `set_feasible`, `set_comprehensible`, `set_validatable`, `set_bounded`); 3 критерия IEEE 830 (`ranked`, `modifiable`, `traceable`).
- `ReqKind`: functional, nonfunctional, data, integration, ui, process, acceptance, api, business, meta.

### `reqcheck/schemas.py` — схемы ответов LLM

Это «черновики» без служебных полей; движок превращает их в объекты `models.py`.

| Схема | Кто возвращает | Содержание |
| :--- | :--- | :--- |
| `SegResult` (`SegItem`) | segment | уточнение вида и summary, добавленные обязательства с цитатами |
| `FindingDrafts` (`FindingDraft`) | review, set.contradictions, set.completeness | список кандидатов в дефекты |
| `ChecklistChecks` (`ChecklistCheck`, `ChecklistStatus`) | set.checklist | ответ по каждому пункту чек-листа: статус, цитата-подтверждение или находка |
| `ScenarioChecks` (`ScenarioCheck`) | set.scenarios | прогон критерия приёмки против правил: согласован ли, ожидаемое по правилам, пропущенные ветки |
| `SetSummaryDraft` (`SetCriterionAssessment`, `SetStatus`) | set.summary | статус по каждому критерию набора |
| `CriticResult` (`CriticVerdict`) | critic | по индексу кандидата: оставить или нет, критичность, уверенность, `duplicate_of` |
| `QuestionDrafts` (`QuestionDraft`) | clarify | вопросы с вариантами |
| `AnswerEffects` (`AnswerEffect`) | clarify (после ответов) | `drop`, `downgrade`, `update`, `new_findings` |
| `VerdictDraft` | verdict | готовность, обоснование, что исправить первым |

## 3. Стадии

| # | Стадия | Модуль | Вход | Выход | LLM-теги |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | Ingest | `ingest/` | путь к файлу | `Document` (блоки с локаторами) | нет |
| 2 | Segment | `segment.py` | `Document` | `list[Requirement]` | `segment` (необязательное уточнение) |
| 3 | Linters | `linters/` | `Document`, требования | `Finding(source=linter)` | нет |
| 4 | Req-Review | `review.py` | требования, находки линтеров | `Finding(source=llm_requirement)` | `review` |
| 5 | Set-Review | `setreview.py` | требования, все находки | `Finding(scope=set)`, затем `SetSummary` | `set.contradictions`, `set.scenarios`, `set.completeness`, `set.checklist`, `set.summary` |
| 6 | Critic | `critic.py` | кандидаты + `grounded` | подтверждённые находки, `verified=True` | `critic` |
| 7 | Clarify | `clarify.py` | проверенные находки | `Question[]`, пересмотр по ответам, `Verdict` | `clarify`, `answers`, `verdict` |
| 8 | Report | `report/` | `ReportData` | `.md`, `.html`, `.json` | нет |

**1. Ingest.** Читатели: PDF (PyMuPDF; восстановление таблиц и заголовков), DOCX (python-docx), Markdown, TXT, HTML. Каждый блок получает локатор (раздел, строка, страница), поэтому PDF, DOCX и MD одного документа дают одинаковый набор требований. Сканы без текстового слоя не читаются.

**2. Segment.** Сначала детерминированный проход: явные идентификаторы (`Ф-1`, `НФТ-2`, `FR-3`, `REQ-12`…) сохраняются как `doc_id`; вид определяется по заголовкам раздела; единица требования равна единице документа (пункт списка, абзац, строка таблицы, код ответа) и **не дробится на предложения**: неатомарность является дефектом, о котором должен сообщить ревьюер. Затем необязательное уточнение LLM: оно может поправить `summary` и `kind` и добавить пропущенные обязательства, но только с подтверждённой цитатой; удалять требования LLM не может.

**3. Linters.** Модули `placeholders`, `vague`, `units`, `api`, `ids` (словари в `lexicon/*.yaml`): заглушки («Да», «Нет», «—», «заполняются…»), слабые слова, смешение денежных единиц (минорные и основные), HTTP-метод против семантики, коды ответов против описаний, нумерация и ссылки. Сбой одного линтера логируется и не останавливает остальные; дубли (заголовок + цитата) удаляются.

**4. Req-Review.** Требования режутся на пакеты (по умолчанию до 7, не пересекая границы раздела), в контекст пакета добавляются заголовки раздела, цели документа и соседние требования. Модель видит находки линтеров по этим требованиям и не дублирует их. Пакеты идут параллельно (`REQCHECK_WORKERS`, по умолчанию 3).

**5. Set-Review.** Четыре вида независимых вызовов, все параллельно:
- *противоречия*: кандидаты — группы требований с общими терминами, числами, именами полей (`engine/terms.py`, без слов конкретного документа); модель судит каждую группу;
- *сценарии*: критерии приёмки прогоняются против правил (например, дата проведения против даты совершения операции); результат превращается в находки с критерием по маркеру в пояснении (`ПРОТИВОРЕЧИЕ`, `НЕОДНОЗНАЧНО`, `НЕ ХВАТАЕТ ДАННЫХ`, `НЕПРОВЕРЯЕМО`);
- *полнота*: ветки процесса, ошибки, NFR и служебные разделы по общему методу, с подсказками из fintech-чек-листа; находки с меткой `[FT-…]` получают `source=fintech`;
- *поштучный чек-лист* (`set.checklist`): каждый применимый пункт `checks/fintech.yaml` и `checks/requirements.yaml` (сквозная согласованность разделов: интерфейс ↔ API, правила ↔ модель данных, цель ↔ NFR, схемы, единые термины, трассировка) получает обязательный ответ `covered / partial / missing / known / not_applicable` с цитатой. Пункты идут пачками по 12 параллельно. Зачем: в одном общем вызове быстрая модель успевала разобрать только часть пунктов, и пропуски вроде «на каком этапе покупка учитывается» терялись. `partial` и `missing` становятся находками с меткой пункта; `known` не дублирует уже найденное.

Оценка набора целиком (`set.summary`, критерии §5.2.6 и IEEE 830) выполняется **после** Critic, чтобы опираться на подтверждённые находки.

**6. Critic.** Сначала детерминированная предварительная дедупликация (пересечение цитат + совпадение семейства критериев; если короткая цитата — лишь фрагмент составного пункта, нужен ещё и похожий заголовок, чтобы разные дефекты одного пункта не склеивались), затем LLM-проверка пакетами (до 25 кандидатов): оставить или отбросить, расставить критичность и уверенность, указать дубль. Находки линтеров с высокой уверенностью и подтверждённой цитатой защищены от отбраковки; после проверки остаются только находки с подтверждённой цитатой или `verified`. Если вердикт по кандидату не пришёл, он остаётся с `verified=False`.

**7. Clarify.** До 15 вопросов-решений по проверенным находкам. В интерактивном режиме (`ask` в `pipeline.run`) ответы передаются в `apply_answers`: находки снимаются, понижаются, обновляются или добавляются новые. Затем `decide()` формирует `Verdict`; детерминированная защита (`guard`) не позволяет вердикту «готово» при наличии критичных находок.

**8. Report.** Шаблоны Jinja2 (`report/templates/`): паспорт, нарезка, проверка требований, проверка набора, сводка, вопросы, итог, приложение с методикой. Находки сортируются по критичности; `fid` присваивается после сортировки (`D-001…`).

## 4. Маршрутизация моделей

`llm.get_client(settings)` строит клиент. Если задан `LLM_STRONG_MODEL`, возвращается `RoutedLLM`: стадия выбирается по **префиксу тега**.

| Тег | Модель при включённой маршрутизации | Причина |
| :--- | :--- | :--- |
| `segment`, `review` | быстрая (`GEMINI_MODEL`, `gemini-3.5-flash-lite`) | много мелких вызовов, нужна скорость (~1–2 с) |
| `set.*` | сильная (`LLM_STRONG_MODEL`, `gemini-3.5-flash`) | межтребовательные рассуждения, противоречия |
| `critic` | сильная | перепроверка находок |
| `clarify`, `answers`, `verdict` | сильная | вопросы, учёт ответов, итог |

**По умолчанию `LLM_STRONG_MODEL` пуст** — все стадии идут в `gemini-3.5-flash-lite` с `LLM_THINKING=high` (измерено: F1 тот же, что с Flash на стадиях рассуждения, при вдвое меньшем времени и без риска исчерпать суточную квоту сильной модели). Набор префиксов настраивается через `LLM_STRONG_TAGS` (по умолчанию `set.,critic,clarify,verdict,answers`). Статистика вызовов обеих моделей суммируется в паспорте. Если сильная модель не задана или совпадает с быстрой, используется один клиент.

## 5. Инфраструктура LLM

Базовый класс `providers/base.py: BaseLLM` реализует общее поведение; провайдер реализует только `_complete_json` и `_classify`.

- **Кэш.** Ключ — sha256 от (провайдер, имя модели из настроек, system, user, JSON-схема, температура); значение — валидированный JSON в `.cache/llm/`. Попадание в кэш пишется в трейс. Отключается `--no-cache`. Битый файл кэша игнорируется.
- **Rate limit.** Скользящее окно `RateLimiter(rpm)` (`LLM_RPM`), потокобезопасное.
- **Повторы.** `RetryableError` (429, 5xx, пустой ответ, таймаут): экспоненциальная задержка от 2 с до 60 с с джиттером; если сервер сообщил `retryDelay`, используется он. Не более `max_retries` (5) попыток. Ошибка схемы: один повтор с текстом ошибки в промпте.
- **Fallback моделей (Gemini).** Цепочка: указанная модель, затем доступные `gemini-X.Y-flash` по убыванию версии, затем `flash-lite`. Переключение: исчерпана суточная квота, 404/403, таймаут, два подряд 503. При пустом `GEMINI_MODEL` модель выбирается пробным запросом (`LLM_PROBE_TIMEOUT`).
- **Структурный вывод.** `response_schema` = pydantic-класс; если модель отвергает схему, схема добавляется в текст промпта (JSON-режим). Если отвергнут `thinking_config`, он отключается для этой модели.
- **Размышления и таймауты.** `LLM_THINKING` (по умолчанию `high`; входит в ключ кэша); таймаут запроса 300 с для Flash и 120 с для Lite (`LLM_REQUEST_TIMEOUT`).
- **Трейс.** `<отчёт>.trace.jsonl`: по строке на вызов (тег, промпты, задержка, токены, признак кэша, номер попытки, ответ, ошибка). Текст ошибок очищается от ключа (`_safe`).
- **Учёт.** `LLMStats`: вызовы, попадания в кэш, токены, разбивка по тегам; попадает в `RunPassport`.
- **FakeLLM.** Детерминированная заглушка для тестов: обработчики по префиксу тега, иначе «пустой» объект схемы.

Провайдеры: `gemini.py` (google-genai), `openai_compat.py` (OpenAI и совместимые через `OPENAI_BASE_URL`), `anthropic.py`, `ollama.py` (локально).

## 6. Контракт промптов

Подробности и плейсхолдеры: [`reqcheck/prompts/README.md`](../reqcheck/prompts/README.md). Кратко:

- промпты на русском, в markdown; структура: роль, входные данные, метод, правила, критичность, формат ответа по `schemas.py`, few-shot пример **из другой предметной области** (не из целевого документа), блок `## ДАННЫЕ` с плейсхолдерами;
- маркер `\n## ДАННЫЕ\n` встречается ровно один раз: всё выше идёт в `system` (вместе с `_common.md`, статично в пределах прогона и потому хорошо кэшируется), всё ниже в `user`;
- фигурные скобки JSON-примеров экранированы `{{ }}`; подставляемые значения экранировать не нужно;
- пустое значение передаётся строкой «нет»;
- `prompt_version` в паспорте считается хэшем содержимого каталога `prompts/`, поэтому любое изменение промптов видно в отчёте;
- каталоги `criteria/*.yaml` и `checks/fintech.yaml` подставляются в промпты (`engine/prompting.py`); fintech-пункты фильтруются по `applies_when` (подстроки в тексте документа).

## 7. Anti-hallucination

1. Промпты требуют дословную цитату и запрещают общие замечания без привязки к тексту.
2. `grounding.find_quote`: нормализация (регистр, пробелы, разметка md, кавычки, тире, `ё→е`, разряды чисел, `тг`→`₸`), точное вхождение (в блоке или на стыке 2–3 соседних блоков), затем нечёткое сопоставление `rapidfuzz.partial_ratio` по блокам и окнам; порог 85. Цитаты с многоточием проверяются по частям. Из найденного блока берётся `location`.
3. Critic и детерминированные правила отбрасывают кандидатов без подтверждённой цитаты.
4. Схемы pydantic, один повтор при нарушении схемы.
5. Температура 0, кэш.

## 8. Оценка (`eval/`)

- `gold.yaml` — 51 эталонный дефект (20 `must_find`), `gold.py` — загрузка, семейства критериев.
- `evaluate.py` — сопоставление находок с эталоном (цитаты + совместимый критерий; опционально `--judge` через `judge.py`), метрики, матрица критичности, таблица абляции (`--compare`).
- `mutate.py` — внесение известных дефектов в `clean_spec.md` по seed, эталон мутанта в `eval/mutants/<seed>.gold.yaml`.
- Результаты: `eval/results/`.

## 9. Расширение

### Добавить линтер

1. Создайте `reqcheck/linters/<имя>.py` с функцией `run(ctx) -> list[Finding]` (`ctx` — `linters.common.Ctx` с документом и требованиями; создавайте находки с точной цитатой, `source=FindingSource.linter`).
2. Добавьте модуль в кортеж в `linters/__init__.py: run_linters`.
3. Словари слов и единиц выносите в `reqcheck/lexicon/*.yaml`.
4. Добавьте тест в `tests/test_linters.py`.

### Добавить провайдера LLM

1. Создайте `reqcheck/providers/<имя>.py` с классом-наследником `BaseLLM`: реализуйте `_complete_json(system, user, json_schema, schema, temperature) -> (текст JSON, число токенов)` и, при необходимости, `_classify(exc)` для преобразования ошибок SDK в `RetryableError` / `QuotaExhausted` / `ModelUnavailable`.
2. Зарегистрируйте имя в `providers/__init__.py: make_client`.
3. Добавьте переменные окружения в `config.py: load_settings` и пример в `.env.example`.

Кэш, лимиты, повторы, трейс и маршрутизацию по стадиям провайдер получает бесплатно.

### Добавить пункт fintech-чек-листа

Добавьте запись в `reqcheck/checks/fintech.yaml` с полями `id` (`FT-<AREA>-NN`), `area`, `question_ru`, `applies_when` (основы слов в нижнем регистре; пустой список — применим всегда), `criterion` (значение `models.Criterion`), `default_severity`, `why_ru`. Пункт попадёт в стадии `set.completeness` и `set.checklist`, если документ содержит одно из ключевых слов. Общие (не предметные) пункты — в `reqcheck/checks/requirements.yaml` с id `RQ-<AREA>-NN`. Кода менять не нужно.

### Добавить критерий или изменить промпт

Критерий добавляется в `criteria/*.yaml` (определение, проверочные вопросы, типичные дефекты, критичность) и в `models.Criterion`. После правки промптов проверьте изменение на мутантах (`eval/mutate.py`), чтобы не подгонять агента под один документ: вписывать в промпты конкретные дефекты целевого документа запрещено.

### Добавить формат входа

Создайте читатель в `reqcheck/ingest/`, возвращающий `Document` с блоками и локаторами, и подключите его в `ingest/__init__.py: load_document`.
