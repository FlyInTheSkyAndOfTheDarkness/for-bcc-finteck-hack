# reqcheck — ИИ-агент проверки требований

Агент статически (без запуска кода) проверяет документ с требованиями на русском языке по **ISO/IEC/IEEE 29148:2018 §5.2.5 / §5.2.6** и **IEEE 830-1998 §4.3** и пишет отчёт на русском: нарезка на требования, замечания к каждому требованию и ко всему набору, сводка, итог «можно ли начинать разработку и тестирование», уточняющие вопросы автору.

Для кого: бизнес-аналитики, системные аналитики и QA банка, которым нужно поймать противоречия, неоднозначности и пропуски **до** начала разработки.

Почему результату можно доверять:

- **Каждое замечание привязано к дословной цитате и месту в документе.** Цитата проверяется нечётким поиском по тексту (grounding); выдуманные цитаты отбраковываются.
- **Детерминированные проверки + LLM.** Правила без LLM (заглушки «Да / Нет», слабые слова, смешение единиц, HTTP-метод против семантики и др.) дают воспроизводимую основу; LLM добавляет смысловые проверки.
- **Critic.** Отдельный проход перепроверяет каждую находку: удаляет необоснованные, склеивает дубли, калибрует критичность.
- **Уточняющие вопросы автору.** Что нельзя решить по тексту, агент превращает в вопросы с вариантами ответа; в режиме `--interactive` ответы учитываются, и находки пересматриваются.
- **Поштучный чек-лист** (45 предметных fintech-пунктов + 14 сквозных): деньги и округление, часовые пояса, жизненный цикл операции, идемпотентность, ИБ и ПДн, эксплуатация, согласованность разделов, критерии приёмки, паспорт. По **каждому** применимому пункту модель обязана вынести вердикт (покрыто / частично / нет / неприменимо) — пункт нельзя «забыть».
- **Измеренное качество:** на документе кейса сдаваемый отчёт (Claude Opus 5.5) находит **92% из 51 эталонного дефекта даже по строгой оценке совпадения цитат, все 20 ключевых (`must_find`) и все 4 критичных** (на PDF-версии — 90%); судья-LLM засчитывает 50 из 51. На **второй, независимой разметке** того же документа — 96%, все 22 ключевых. Из находок вне эталона ошибочны 3%. На бесплатном Gemini — 78% по строгой оценке. См. [Оценка качества](#оценка-качества).

## Быстрый старт

Нужен **Python 3.11+**.

```bash
# 1. Окружение
python -m venv .venv
```

Активация:

```powershell
# Windows PowerShell
.venv\Scripts\Activate.ps1
```
```bash
# Linux / macOS / Git Bash
source .venv/bin/activate        # в Git Bash на Windows: source .venv/Scripts/activate
```

```bash
# 2. Зависимости (3–5 минут)
pip install -r requirements.txt
```

### Как получить ключ LLM (бесплатно, без карты)

1. Откройте <https://aistudio.google.com/> и войдите Google-аккаунтом.
2. **Get API key → Create API key**.
3. Скопируйте ключ.

### Куда положить ключ

```powershell
# Windows PowerShell
copy .env.example .env
```
```bash
# Linux / macOS / Git Bash
cp .env.example .env
```

Откройте `.env` и вставьте ключ в строку `GEMINI_API_KEY=...`. Файл `.env` исключён из git; в репозитории лежит только пример `.env.example` без ключа.

### Запуск проверки (одна команда)

Перед запуском: venv активирован, в `.env` указан ключ (без ключа команда завершится с кодом 2 и подсказкой).

```bash
python -m reqcheck docs/requirements.md -o reports/report.md
```

Вход с PDF (обязательный формат кейса; также `.docx`, `.md`, `.txt`, `.html`):

```bash
python -m reqcheck docs/requirements.pdf -o reports/report_pdf.md
```

### Где лежит результат

Для `-o reports/report.md` агент создаёт рядом:

| Файл | Что это |
| :--- | :--- |
| `reports/report.md` | отчёт на русском (основной) |
| `reports/report.html` | то же со стилями и навигацией (отключается `--no-html`) |
| `reports/report.json` | полные структурированные данные прогона (вход для `eval`) |
| `reports/report.trace.jsonl` | журнал всех вызовов LLM: стадия, задержка, токены, ответ (ключ в журнал не попадает) |

### Сколько ждать

- **Первый прогон — около 4 минут** (измерено: ~235 с, ~29 вызовов LLM на документ кейса) с настройками по умолчанию (`gemini-3.5-flash-lite`, `LLM_THINKING=high`). С сильной моделью (`LLM_STRONG_MODEL=gemini-3.5-flash`) — ~6+ минут: на бесплатном тарифе она отвечает 30–250 с на запрос. Если суточная квота основной модели исчерпана, прогон идёт на запасных моделях и может занять 15–50 минут (ожидание 429/503).
- **Повторный прогон того же документа — секунды:** ответы LLM кэшируются на диске в `.cache/llm/` по хэшу запроса.
- `--no-cache` — прогон «с нуля», без кэша.

### Демо без ключа

```bash
python -m reqcheck docs/requirements.md -o reports/demo.md --provider fake
```

Режим `fake` не обращается к внешней LLM: отработают чтение, нарезка и детерминированные проверки, а LLM-стадии получат пустые ответы встроенной заглушки (счётчик «вызовов LLM» в выводе считает обращения к заглушке; журнал `.trace.jsonl` создаётся пустым). Подходит, чтобы убедиться, что установка работает, но **не** показывает качество агента.

## Параметры CLI

`python -m reqcheck [параметры] input`

| Параметр | Описание |
| :--- | :--- |
| `input` | файл требований: `.pdf` `.docx` `.md` `.txt` `.html` |
| `-o`, `--output` | файл отчёта `.md` (по умолчанию `reports/report.md`); рядом создаются `.html`, `.json`, `.trace.jsonl` |
| `--provider` | `gemini` \| `openai` \| `anthropic` \| `ollama` \| `fake` (иначе из `LLM_PROVIDER`) |
| `--model` | имя модели; иначе из `.env` или автоматический выбор |
| `--interactive` | задать уточняющие вопросы в терминале и учесть ответы |
| `--no-cache` | не использовать кэш ответов LLM |
| `--no-html` | не создавать HTML-версию отчёта |

Код возврата `2` — не задан ключ для выбранного провайдера.

## Настройки `.env`

| Переменная | По умолчанию | Назначение |
| :--- | :--- | :--- |
| `LLM_PROVIDER` | `gemini` | `gemini`, `openai`, `anthropic`, `ollama` |
| `GEMINI_API_KEY` | — | ключ Gemini (обязателен для `gemini`) |
| `GEMINI_MODEL` | `gemini-3.5-flash-lite` | быстрая модель для массовых проверок. Пусто: агент сам перебирает доступные Flash-модели (~1,5 мин) |
| `LLM_STRONG_MODEL` | пусто | сильная модель для рассуждений (например `gemini-3.5-flash`). Пусто: всё делает `GEMINI_MODEL` |
| `LLM_STRONG_TAGS` | `set.,critic,clarify,verdict,answers` | какие стадии (по префиксу тега) идут в сильную модель |
| `LLM_RPM` | `8` | лимит запросов в минуту (бесплатный тариф) |
| `LLM_TEMPERATURE` | `0` | температура; 0 для воспроизводимости |
| `LLM_THINKING` | `high` | режим размышлений Gemini: `off` \| `minimal` \| `low` \| `medium` \| `high`. Входит в ключ кэша |
| `GEMINI_FALLBACK_MODELS`, `LLM_STRONG_FALLBACK_MODELS` | авто | запасные модели через запятую для быстрой и сильной модели |
| `LLM_REQUEST_TIMEOUT` | 300 с (Flash), 120 с (Lite) | таймаут одного запроса, секунды |
| `OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_BASE_URL` | — | OpenAI или любой OpenAI-совместимый сервер |
| `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL` | — | Anthropic |
| `OLLAMA_BASE_URL`, `OLLAMA_MODEL` | `http://localhost:11434`, `qwen2.5:14b` | локальная модель |

Дополнительно: `REQCHECK_WORKERS` (по умолчанию 3) — число параллельных запросов внутри стадии; `LLM_PROBE_TIMEOUT` (30 с) — таймаут пробного запроса при автовыборе модели; `REQCHECK_SKIP=review,set,checklist,critic,clarify` — отключить стадии (для абляции); `LLM_RECOVER_S` (60 с) — через сколько секунд после ухода на запасную модель снова пробовать основную.

## Интерактивный режим и веб-интерфейс

**Интерактивный режим.** После проверки агент задаёт автору документа уточняющие вопросы (до 15) с вариантами ответа:

```bash
python -m reqcheck docs/requirements.md -o reports/report_interactive.md --interactive
```

Ответ: номер варианта, свой текст или Enter (пропустить). Ответы учитываются: часть находок снимается или снижается по критичности, могут добавиться новые, итог пересчитывается.

**Веб-интерфейс (Streamlit):**

```bash
streamlit run app.py
```

Загрузка файла (или встроенные примеры `docs/requirements.md` и `.pdf`), выбор провайдера (в том числе `fake` для демо без ключа), прогресс по стадиям, вкладки с нарезкой, замечаниями, вопросами (поля для ответов с пересчётом) и итогом, скачивание MD/HTML. Результаты UI-прогонов складываются в `reports/ui/<время>/`.

## Используемая модель

**Сдаваемый отчёт** сделан на **Claude Opus 5.5** (`--provider anthropic`, `LLM_EFFORT=medium`): один прогон — 30 вызовов, ~585 тыс. токенов, 6,5 минуты, порядка нескольких долларов. **Бесплатный вариант по умолчанию** — **Gemini `gemini-3.5-flash-lite` с режимом размышлений `high`** (Google AI Studio): качество ниже, зато ключ бесплатный. Опционально включается маршрутизация по стадиям (`RoutedLLM`, `LLM_STRONG_MODEL`):

| Роль | Модель | Стадии (теги) |
| :--- | :--- | :--- |
| Быстрая (по умолчанию — все стадии) | `gemini-3.5-flash-lite` | нарезка (`segment`), проверка требований (`review`) и, если сильная модель не задана, всё остальное |
| Сильная (опционально) | `gemini-3.5-flash` | противоречия, сценарии, полнота набора, сводка (`set.*`), Critic (`critic`), вопросы (`clarify`), ответы (`answers`), итог (`verdict`) |

**Почему так (измерено на бесплатном тарифе).** Lite отвечает за 1–20 с, Flash — за 30–250 с и чаще получает 503/504. Главный рычаг качества оказался не в размере модели, а в режиме размышлений: `LLM_THINKING=high` на Lite заметно увеличил число найденных противоречий и пропусков. Сравнение холодных прогонов: Lite+high — F1 62%, 197 с; Lite+Flash — F1 62%, 375 с (разница в пределах разброса между прогонами). Поэтому по умолчанию — Lite: вдвое быстрее и не упирается в суточную квоту сильной модели.

**Запасная цепочка.** Если модель недоступна (404/403), исчерпана суточная квота, превышен таймаут или два подряд ответа 503, агент переключается на следующую модель цепочки (цепочка кольцевая: модели, ответившие 404 или исчерпавшие квоту, исключаются до конца прогона, а на основную модель агент возвращается через `LLM_RECOVER_S` секунд после временного сбоя): для явно заданной модели — Flash той же или более ранней версии, затем Lite (или список из `GEMINI_FALLBACK_MODELS` / `LLM_STRONG_FALLBACK_MODELS`). Ошибки 429 обрабатываются с экспоненциальной задержкой и учётом `retryDelay` сервера. Все модели, которые реально отвечали, перечислены в паспорте отчёта.

**Другие провайдеры.** Всё идёт через один интерфейс `LLMClient.generate_json`, поэтому подключаются OpenAI и OpenAI-совместимые серверы, Anthropic и **Ollama**. Ollama запускает модель локально: для банка это значит, что **текст требований не покидает периметр**.

```bash
# пример: локальная модель
python -m reqcheck docs/requirements.md -o reports/report_local.md --provider ollama --model qwen2.5:14b
```

Провайдеры OpenAI и Anthropic требуют установки SDK (`pip install openai` или `pip install anthropic`). **Anthropic:** модель по умолчанию `claude-opus-5-5`, ответ строго по JSON-схеме (структурированный вывод), адаптивные размышления с глубиной `LLM_EFFORT` (по умолчанию `high`), серверный запасной маршрут при отказе модели; `temperature` не передаётся (у текущих моделей Claude её нет), воспроизводимость даёт кэш.

## Как это работает

```
файл ─► 1 Ingest ─► 2 Segment ─► 3 Linters ─► 4 Req-Review ─► 5 Set-Review ─► 6 Critic ─► 7 Clarify ─► 8 Report
        блоки +      требования    правила,     каждое         набор целиком   проверка    вопросы +    MD / HTML /
        локаторы     + цитаты      без LLM      требование                     находок     итог         JSON / trace
```

| # | Стадия | Что делает |
| :--- | :--- | :--- |
| 1 | Ingest | PDF (PyMuPDF), DOCX, MD, TXT, HTML → блоки с локаторами (раздел, строка, страница) |
| 2 | Segment | правила нарезки (Ф-N, строки таблиц, параметры API, статусы) + LLM-доуточнение; присваивает `R-01…`, сохраняет `doc_id` и цитату |
| 3 | Linters | детерминированные проверки: заглушки, слабые слова, единицы, HTTP-методы и коды ответов, нумерация |
| 4 | Req-Review | LLM проверяет пакеты требований по критериям ISO 29148 §5.2.5 |
| 5 | Set-Review | противоречия по парам-кандидатам, прогон критериев приёмки против правил, полнота набора, **поштучный чек-лист** (вердикт по каждому из ~59 пунктов, пачками по 12), оценка набора по §5.2.6 / IEEE 830 |
| 6 | Critic | отбрасывает необоснованное, объединяет дубли, ставит критичность и уверенность |
| 7 | Clarify | уточняющие вопросы автору, учёт ответов, итог (готовность к разработке и тестированию, что исправить первым) |
| 8 | Report | паспорт прогона, таблицы и разделы отчёта |

**Источники критериев:** `reqcheck/criteria/iso29148.yaml` (9 критериев отдельного требования §5.2.5 и 6 критериев набора §5.2.6, языковые рекомендации §5.2.7), `reqcheck/criteria/ieee830.yaml` (ranked, modifiable, traceable, перекрёстные ссылки §4.3). **Чек-листы:** `reqcheck/checks/fintech.yaml` (45 предметных пунктов) и `reqcheck/checks/requirements.yaml` (14 сквозных пунктов: API покрывает все операции интерфейса, модель данных покрывает правила, цель согласована с NFR, схемы, термины, перечни, критерии приёмки, трассировка, паспорт); на каждый документ применяются пункты, чьи ключевые слова в нём встречаются.

**Защита от галлюцинаций:** (1) модель обязана привести дословную цитату; (2) цитата проверяется нечётким сопоставлением с текстом документа (`rapidfuzz`, порог 85), в отчёте помечается подтверждение; (3) Critic перепроверяет находки; (4) ответы LLM валидируются по JSON-схемам (pydantic), при нарушении схемы запрос повторяется один раз с описанием ошибки; (5) температура 0.

Подробности: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## Состав отчёта (соответствие §6 ТЗ организаторов)

| Требование ТЗ | Раздел отчёта |
| :--- | :--- |
| Паспорт прогона: документ, дата, модель, версия агента | 1. Паспорт прогона (плюс хэш документа, версия промптов, число вызовов и токенов, длительность) |
| Как агент нарезал требования | 2. Нарезка требований: таблица «ID в отчёте — ID в документе — формулировка», с цитатами |
| Проверка каждого требования | 3. Проверка каждого требования |
| Проверка всего набора | 4. Проверка набора требований целиком |
| Сводка: число требований, нарушения, критичные дефекты | 5. Сводка |
| Уточняющие вопросы | 6. Уточняющие вопросы автору документа |
| Итог: можно ли начинать разработку и тестирование, что исправить первым | 7. Итог |

Каждое замечание содержит критерий, критичность, цитату, место в документе, объяснение и рекомендацию. Общих фраз без привязки к тексту в отчёте нет.

## Оценка качества

Агент измеряется, а не только демонстрируется.

- **Gold-набор** `eval/gold.yaml`: 51 дефект документа `docs/requirements.md` с цитатами, критерием и критичностью; из них 20 помечены `must_find` (ключевые, которые обязан найти любой хороший ревьюер). Разметка сделана вслепую, независимо от промптов и отчётов агента.
- **Метрики:** recall (общий, по `must_find`, по критичности и критериям), precision, F1, дубликаты, согласие по критичности. Сопоставление находки с эталоном: сходство цитат + совместимый критерий; опционально судья-LLM (`--judge`).

```bash
python -m reqcheck docs/requirements.md -o reports/report.md
python -m eval.evaluate reports/report.json --out eval/results/full.md
# сопоставление пакетным вызовом LLM вместо лексического:
python -m eval.evaluate reports/report.json --judge --out eval/results/full_judge.md
# таблица абляции по нескольким прогонам:
python -m eval.evaluate --compare reports/ablation/linters_only.json reports/report.json --out eval/results/ablation.md
```

Параметры `eval.evaluate`: `--gold` (путь к эталону), `--threshold` (порог похожести цитат, по умолчанию 80), `--any-criterion` (не требовать совместимости критерия).

**Проверка на переобучение (мутационное тестирование).** Запрещено вписывать в промпты конкретные дефекты целевого документа. Чтобы это проверить, `eval/mutate.py` вносит известные дефекты в чистую спецификацию `eval/clean_spec.md` и пишет эталон для каждого мутанта:

```bash
python -m eval.mutate --seed 1 --n 5
python -m reqcheck eval/mutants/1.md -o reports/mutant1.md
python -m eval.evaluate reports/mutant1.json --gold eval/mutants/1.gold.yaml
```

### Результаты: сдаваемый отчёт (`v1.2.4`, Claude Opus 5.5, `LLM_EFFORT=medium`)

```bash
python -m reqcheck docs/requirements.md -o reports/report.md --provider anthropic
```

Два прогона Claude: Markdown и PDF того же документа. Они независимы, кэш не общий, потому что нарезка PDF даёт другие тексты запросов.

| Прогон | Recall (из 51) | must_find (из 20) | critical (из 4) | Precision | F1 | Recall, судья | Замечаний |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| `reports/report.md` | **92%** | **20/20** | **4/4** | 76% | **83%** | 98% | 92 (из них 13 «под сомнением») |
| `reports/report_pdf.md` (вход — PDF) | 90% | 20/20 | 4/4 | 76% | 82% | 98% | 83 (из них 8 «под сомнением») |
| только подтверждённые, MD / PDF | 84% / 84% | 18 / 18 | 4 / 4 | 78% / 79% | 81% / 81% | | 79 / 75 |

Recall и precision здесь лексические, то есть строгие, по совпадению цитат. Файлы: `eval/results/final*.md`, `final_pdf*.md`. Разброс между двумя прогонами — 2 пункта recall. Судья пропустил по одному дефекту в каждом прогоне: G-10 и G-11. Лексически не засчитаны ещё несколько находок, которые в отчёте есть, но с цитатой из другого места.

**Проверка самой оценки** (подробно — `eval/results/audit.md`). Проверял отдельный экземпляр LLM-аналитика, которому не показывали эталон и код агента. Это не человек-эксперт.

- **Вторая независимая разметка документа** (`eval/gold_independent.yaml`): 48 дефектов, все 4 critical совпадают с нашими. 96% её пунктов есть в нашем эталоне. Агент на Claude находит **96% второй разметки (судья), все 22 ключевых и все 4 critical**; по цитатам — 83%. Значит, результат не подогнан под собственный эталон.
- **Аудит 22 находок, не совпавших с эталоном:** 9 — настоящие дефекты вне эталона, 9 — придирки, 1 — дубль, 3 — ошибочные. С учётом аудита верных находок 86% (79 из 92), ошибочных 3%.
- **Шум на чистом ТЗ** (`eval/clean_spec.md`, внесённых дефектов нет):
  - у обеих моделей 0 critical;
  - в приложении «под сомнением» нет ни одного верного замечания;
  - у Claude ошибочных 10% подтверждённых замечаний (у Gemini 30%), остальное — придирки и дубли.
  Отрезать minor нельзя: recall на документе кейса упал бы с 92% до 47%.

Отчёты той же версии агента на бесплатном Gemini сохранены для сравнения: `reports/report_gemini.md`, `reports/report_pdf_gemini.md` (`eval/results/gemini_final*.md`).

### Результаты на бесплатном Gemini (версия `v1.2`, `gemini-3.5-flash-lite`, `LLM_THINKING=high`)

Два способа сопоставить находку с эталоном:

- **лексический** (по умолчанию) — совпадение цитат + совместимый критерий. Строгая нижняя граница: если агент описал тот же дефект, но процитировал другое место (например, строку таблицы вместо заголовка), находка не засчитывается;
- **судья-LLM** (`--judge`) — один пакетный вызов модели решает, описывает ли находка тот же дефект. Ближе к оценке человеком; precision судьи завышена (он склонен сопоставлять каждую находку хоть с чем-то), поэтому precision приводим лексическую.

**Документ кейса, три независимых холодных прогона** (ответы LLM различаются от прогона к прогону даже при температуре 0, поэтому приводим среднее, а не лучший прогон):

| Прогон | Recall, судья | must_find, судья | critical, судья | Recall, лексич. | must_find, лексич. | Precision, лексич. | F1, лексич. | Замечаний |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| прогон 1 (`reports/report_gemini.md`) | 90% | 20/20 | 4/4 | 74% | 18/20 | 78% | 76% | 72 (из них 12 «под сомнением») |
| холодный прогон 2 | 96% | 20/20 | 4/4 | 84% | 18/20 | 78% | 81% | 72 |
| холодный прогон 3 | 88% | 20/20 | 4/4 | 74% | 18/20 | 84% | 79% | 68 |
| **среднее** | **91%** | **20/20** | **4/4** | **78%** | **18/20** | **80%** | **79%** | |
| тот же документ в **PDF** (`reports/report_pdf_gemini.md`) | 86% | 19/20 | 4/4 | 80% | 18/20 | 86% | 83% | 65 |

Каждый из 51 эталонного дефекта найден хотя бы в одном прогоне. Только подтверждённые замечания (без приложения «под сомнением», `--confirmed-only`), лексически: recall 75%, precision 83%, F1 78% в среднем. Файлы: `eval/results/gemini_final*.md`, `stats_cold2*.md`, `stats_cold3*.md`, `final_pdf*.md`.

**`v1.2.2`** закрывает два системных пропуска, найденных разбором этих прогонов: точная находка линтера («в поле «Задача в JIRA» нет ключа задачи») больше не поглощается широкой LLM-находкой при склейке дублей, и добавлены пункты чек-листа о предусловиях и покрытии критериев приёмки (G-49 и G-25 теперь находятся). Контрольные прогоны `v1.2.2` пришлось делать на запасной `gemini-3.1-flash-lite` (суточная квота основной модели была исчерпана): судья — recall 84–90%, must_find 19/20, critical 4/4 (`eval/results/v122_*.md`). Итог по моделям: Claude Opus 5.5 на том же агенте поднимает строгий recall с 78% (среднее Gemini) до 92% и закрывает все ключевые дефекты даже по строгой оценке — архитектура агента не привязана к модели, а качество растёт вместе с ней.

**Абляция по стадиям** (стадии отключаются через `REQCHECK_SKIP`, ответы LLM остальных стадий из кэша; лексическая оценка):

| Конфигурация | Recall | must_find | critical | Precision | F1 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Только линтеры (без LLM), `v1.1` | 29% | 11/20 | 1/4 | 86% | 44% |
| + проверка каждого требования (LLM), `v1.1` | 63% | 14/20 | 2/4 | 75% | 68% |
| + проверка набора: противоречия, сценарии, полнота, `v1.1` | 75% | 16/20 | 3/4 | 76% | 75% |
| + Critic, `v1.1` | 71% | 15/20 | 3/4 | 75% | 72% |
| `v1.2` без поштучного чек-листа | 63% | 14/20 | 3/4 | 77% | 69% |
| **`v1.2` полный агент** (+ поштучный чек-лист, сквозные пункты) | **74%** | **18/20** | **4/4** | **78%** | **76%** |

Поштучный чек-лист — самый сильный рычаг `v1.2`: +11 п. п. recall и +4 ключевых дефекта на том же кэше остальных стадий (`eval/results/ablation_no_checklist.md`). Critic почти не меняет precision, зато склеивает дубли и отделяет сомнительное: на Lite-модели отклонённые им находки оказались в основном верными, поэтому он их **не удаляет**, а выносит в приложение «под сомнением» (не влияет на итог).

**История улучшений** (лексическая оценка, среднее холодных прогонов): исходные промпты — recall 37%, F1 51% → `v1.1` (настройка промптов без подгонки под эталон, режим размышлений) — recall 68%, F1 71% → `v1.2` (поштучный чек-лист, сквозные пункты) — recall 78%, must_find 18/20, F1 79%. Промежуточные замеры — `eval/results/tuning/`.

**Мутационное тестирование** (чистое ТЗ другой предметной области + 5 внесённых дефектов на seed): найдено **5/5** в обоих мутантах (`eval/results/final_m1.md`, `final_m2.md`, код `v1.2`). Precision на мутантах низкая по построению: агент находит и настоящие мелкие недочёты в невнесённых местах, которых нет в эталоне мутанта.

**Чистая спецификация** (`eval/clean_spec.md`, без внесённых дефектов): 0 критичных замечаний у обеих моделей. Независимый аудит каждого замечания — в `eval/results/audit.md`: на Claude ошибочных 10%, на Gemini 30%, в приложении «под сомнением» верных нет ни одного. Остальной шум — мелкие придирки и дубли: обратная сторона высокого recall.

## Ограничения

- **Бесплатный тариф:** ограничены число запросов в минуту и суточная квота (сбрасывается в полночь по тихоокеанскому времени, ~13:00 по Астане). При исчерпании квоты агент переключается на запасную модель, качество может снизиться.
- **PDF.** Поддерживаются PDF с текстовым слоем. Сканы без OCR не распознаются; сообщение pymupdf «RapidOCR is missing» при обычном PDF безвредно.
- **Разброс между прогонами.** Даже при температуре 0 ответы LLM немного отличаются от прогона к прогону; поэтому метрики качества приведены как среднее по нескольким холодным прогонам. Кэш делает повторный прогон того же документа детерминированным.
- **Сканированные PDF без текстового слоя не поддерживаются** (OCR нет). PDF с текстовым слоем читается; сложные таблицы в PDF восстанавливаются эвристиками и могут быть неточны.
- **Недетерминизм LLM:** снижается температурой 0 и дисковым кэшем (повторный прогон даёт тот же результат), но другая версия модели или `--no-cache` могут дать немного другой набор находок.
- Агент проверяет **текст**, а не предметную правильность: например, не знает внутренних политик банка, которых нет в документе. На такие места он задаёт вопросы.
- **Шум на хороших документах.** Поштучный чек-лист повышает recall, но на чистой спецификации даёт десятки мелких замечаний (в основном придирки и дубли; ошибочных — 10% на Claude), критичных — 0. Читайте по критичности; приложение «под сомнением» можно пропустить — в аудите в нём не нашлось ни одного верного замечания.
- **Оценка — на одном документе.** Эталонов два (наш и независимый), но документ кейса один; на других предметных областях проверены только мутанты чистого ТЗ. Независимые проверки сделаны LLM-аналитиком, а не человеком.
- **Лексическая оценка — нижняя граница.** Она не засчитывает верную находку с цитатой из другого места; поэтому приводим и оценку судьёй-LLM.
- Критичность и итог «готово / не готово» остаются рекомендацией; решение принимает человек.
- Режим `fake` не показывает качество агента (нет LLM-стадий).

## Безопасность

- Ключи хранятся только в `.env` (в `.gitignore`); в репозитории только `.env.example` без ключа.
- Ключ не попадает в журнал `*.trace.jsonl` и в сообщения об ошибках (подменяется на `***`).
- Кэш `.cache/`, отчёты UI (`reports/ui/`) и любые новые файлы в `reports/` исключены из git; в репозитории лежат только итоговые отчёты прогона по документу кейса (`reports/report.*`, `reports/report_pdf.*`) и данные абляции.
- Для данных, которые нельзя отправлять во внешние сервисы, используйте `--provider ollama` (локальная модель).
